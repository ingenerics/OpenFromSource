# Research: Bootstrap Operator System

**Feature**: [spec.md](spec.md) | **Phase 0** — decisions consolidated from the feature request, constitution, and hands-on experiments on Debian Trixie (apt 2.9.x, this development machine).

## Decision 1: Operator side is a bash script (optional cache-dir argument, default = its own location); admin side is a `package_mgmt` command

- **Decision**: The bootstrap is delivered as `bootstrap.sh` generated into `{binary_cache}/handoff/` by a new admin-only `package_mgmt handoff` command. The operator runs `{cache}/handoff/bootstrap.sh` — the cache directory is an **optional positional argument** (a given path is used as-is) defaulting to the cache the script ships in (the handoff's parent directory), so a normally-placed cache needs no argument at all; `--remove` unconfigures.
- **Rationale**: The feature request explicitly asks to prefer a bash script when it's simpler. FR-007 demands the bootstrap run on a bare DVD base install with no additional software — `package_mgmt` itself is NOT on the operator system (it lives in the project repo, not the handoff), so a `package_mgmt bootstrap` command would force shipping a Python toolchain in the handoff: the opposite of friction-free. On the operator side the script only needs `bash`, `apt`, and coreutils (all guaranteed on a standard base install). The admin side, by contrast, must parse the database and the cached archive indexes and generate deb822 index files — `package_mgmt` already has exactly those services (spec 010/011), so a bash reimplementation (requiring `sqlite3`/`python3` and reimplementing index parsing) would be strictly more machinery. **Path resolution**: the script derives the cache from its own location (the handoff's parent) by default and accepts an optional override argument, because the settings merge (defaults + local overrides, `{base_dir}` expansion, absolute sub-dir overrides) is too much machinery for a bash script to reimplement faithfully — and it doesn't need to: the handoff is self-describing (release/components from its own `dists/` tree, pool via its symlink), so the script's only input is *where the cache is*, and a given argument is authoritative. The settings files remain the admin side's concern (`handoff` runs with the real merged config).
- **Alternatives considered**:
  - `package_mgmt bootstrap` command on the operator system — rejected: requires installing the tool + Python + `python-debian` on a system that must receive no additional software (FR-007).
  - Python-based path resolution (vendoring `config_loader` semantics or shipping the package) — rejected: one path lookup does not justify a Python dependency on the operator system (python3 is not guaranteed on a minimal base install), and the handoff is self-describing so no settings parsing is needed at all.
  - Pure-bash admin-side generator (awk/grep over the DB) — rejected: needs `sqlite3` CLI (not in base install) and reimplements deb822 parsing that `python-debian` already provides.
  - `apt-offline` bundle generation (roles.md's bundle workflow) — rejected: `apt-offline` targets a different model (bundled transfer + `sync` ingest); the cache is already an apt-archive-shaped directory, so direct `file://` consumption is one order of magnitude simpler.

## Decision 2: The apt source is `file://` with `signed-by`; the signed `Release.gpg` ships for constitutional compliance

- **Decision**: Operator's sources entry: `deb [signed-by={cache}/handoff/offline-cache.gpg] file:{cache}/handoff {release} {components}`. The handoff contains `Release` + an armored detached signature `Release.gpg` (generated and signed admin-side with a cache-local key, public part shipped as `offline-cache.gpg`). The operator never runs `gpg`, never manages keys, and never works around trust warnings (FR-009/SC-006). `signed-by` pins exactly the cache's own key, so the repository's signature is *verified* — no `[trusted=yes]` trust workaround is needed.
- **Rationale**: Empirically verified on a test system (apt 3.0.3, Debian Trixie) with the generated handoff and a scratch repository:
  - The `Release` file must NOT contain a trailing blank line between the metadata headers and the hash blocks: in Debian control format a blank line terminates the section, so apt never parses `MD5Sum`/`SHA1`/`SHA256`/`SHA512` → "No Hash entry in Release file" + "provides only weak security information" (this blank line was the root cause of the earlier "unavoidable for file://" observations).
  - The `Release` hash blocks must list BOTH `{component}/binary-amd64/Packages` (the file apt fetches and verifies for `file://`) AND `.../Packages.gz` (what is physically shipped) — a `Packages.gz`-only hash list makes apt drop the index once hashes are parsed ("Unable to locate package").
  - With those two conditions met, `deb [signed-by=.../offline-cache.gpg] file:/...` → `apt update` exit 0 with ZERO warnings and the index IS fetched; tampering with `Release` after signing makes apt refuse with "The repository ... is not signed" (signature enforced).
  - The `Release` file's checksums of the index files ARE enforced by apt regardless (an experiment with missing hash entries made the index be dropped: "Unable to locate package").
- **Alternatives considered**:
  - `[trusted=yes]` (no `signed-by`) — rejected: apt still attempts signature verification and warns "Missing key ... needed to verify signature" on every `apt update`, and the signature is never actually enforced.
  - Serve the cache via a local HTTP daemon on the operator system (`http://127.0.0.1:PORT`) to enable full signature enforcement — rejected for this feature: adds a service with lifecycle/restart concerns to every operator system, violating the explicit "don't over-engineer" instruction, and unnecessary since `file://` + `signed-by` already verifies the signature.
  - Installing the key into `/etc/apt/trusted.gpg.d/` — rejected: touching the system keyring makes `--remove` untidy and adds nothing when `signed-by` already pins the key per-source.

## Decision 3: The offered package set is a *filtered* index generated from the cache's own verified state

- **Decision**: The handoff generator emits, per present (release, component), a `Packages.gz` containing exactly the paragraphs of current binaries with `verified = 1` whose pool file exists, enriched with `Filename`/`Size`/`SHA256`/`Depends`/`Provides` from the cached archive index (the arch-aware lookup introduced in spec 011). A `Release` file lists checksums of these indexes; `Release.gpg` is its armored detached signature.
- **Rationale**: The cache's own `dists/` indexes describe the FULL archive (fetched by `init`/`add`), while the pool holds only the verified subset (spec 011). Pointing apt at the full index would offer packages whose files don't exist (FR-003 violation: "every offered package MUST be installable"). Deriving the offered set from `binaries.verified` + the index's file metadata keeps the spec 010/011 "database stores state, indexes store metadata" design intact; nothing is guessed.
- **Alternatives considered**:
  - Serve the full archive index — rejected: lists phantom packages (FR-003).
  - Overwrite the cache's own `dists/` indexes with the filtered ones — rejected: breaks `add`/`download`/`verify` re-runs (index-read design).
  - Copy the pool into the handoff — rejected: duplicates storage (Constitution IV); the `pool` symlink serves files in place instead.

## Decision 4: Handoff layout and key handling

- **Decision**: `{binary_cache}/handoff/` holds `dists/{release}/Release`, `Release.gpg`, `{component}/binary-amd64/Packages.gz` (filtered), `offline-cache.gpg` (armored public key), `bootstrap.sh`, and a `pool -> ../pool` symlink (re-created by the script if missing — survives media that can't carry symlinks, e.g. FAT USB).
- **Rationale**: Keeping the derived source in its own subtree guarantees the project's archive indexes are never mutated. The private key is generated into the handoff at generation time and kept there: the cache IS the trust domain (admin-verified, physically handed over); the operator system trusts exactly this key via `signed-by`. Re-running `handoff` regenerates the key and all artifacts idempotently.
- **Alternatives considered**: sign with a long-lived project key — rejected: key escrow and distribution complexity for no gain on a per-cache trust model; per-cache keys keep every cache's trust anchor self-contained.

## Decision 5: Release metadata details (empirically constrained)

- **Decision**: `Release` contains `Origin`, `Label`, `Suite`/`Codename` (the cache's release), `Architectures: amd64`, `Components` (the present ones), `Date`, `Valid-Until` (+1 year from generation), and `MD5Sum`/`SHA1`/`SHA256`/`SHA512` blocks with index paths relative to `dists/{release}/`. `Release.gpg` is its armored detached signature.
- **Rationale**: The +1y `Valid-Until` prevents apt's "release file expired" failure on long-lived offline systems; re-running the bootstrap refreshes it. Relative index paths are mandatory for apt's hash lookup (verified: absolute-style paths were not resolved and the index was dropped). The signature MUST be an armored detached `Release.gpg` (verified: a clearsigned `InRelease` breaks the `file://` index fetch entirely; binary detached signatures hit "unsupported binary format" via the `file://` method; armored detached works).
- **Alternatives considered**: detached `Release.gpg` — works armored but adds a second file with no benefit; omitting `Valid-Until` — risks expiry errors on long-lived systems.

## Decision 6: Bootstrap script behavior and validation scope (FR-004/005/006/008)

- **Decision**: The script (a) validates its invocation (at most one cache-dir argument, used as-is when given; the default is the handoff's parent directory) and preflights as non-root → clear error; (b) validates the handoff structure at the given path (`Release.gpg` present, per-component `Packages.gz` present, `pool` target exists) and the release match (handoff release == `VERSION_CODENAME` in `/etc/os-release`, else clear refusal); (c) writes `/etc/apt/sources.list.d/openfromsource-cache.list` atomically (idempotent — overwrites its own prior entry only, never other files); (d) re-creates the `pool` symlink if missing; (e) runs `apt update` and reports success/errors with exit 0/1. `--remove` (with the same cache-dir argument) deletes the entry and re-runs nothing; the key file stays in the cache (harmless, referenced only by the removed entry). Failures BEFORE the entry is written leave the system's apt configuration untouched (the entry is written last, after validation); an `apt update` failure after the write leaves the entry in place for inspection per FR-006.
- **Rationale**: All checks are expressible in a few lines of bash using only base-install tools. Deep verification (per-file checksums of the whole pool) belongs to the admin's `verify` pre-handoff; operator-side verification is **deferred** — the operator cannot run `package_mgmt verify` on a bare install (FR-007: no additional software installation), so the bootstrap preflight is structural (handoff structure + release match) only. The handoff generator itself only includes records whose pool file exists, so the offered set is consistent by construction.
- **Alternatives considered**: deep integrity re-check inside the script — rejected as over-engineering (would duplicate `verify`, which is unavailable on the operator system; deferred to a future operator-side verify capability); interactive prompts — rejected (FR-001 single action).

## Decision 7: deb-src (source packages) is out of scope

- **Decision**: The handoff exposes binary packages only (`deb` lines, no `deb-src`). The source pool built by spec 011 is untouched and remains available to the project's own tooling.
- **Rationale**: The spec's stories and FRs concern package installation (binaries); `deb-src` support would add `Sources.gz` filtering, per-source keys, and `apt-get source` semantics without a driving requirement. Constitution III's rebuild guarantee is served by the source pool's existence (spec 011), not by apt-level source exposure.
- **Alternatives considered**: shipping `deb-src` lines now — rejected (scope; IX); revisit in a future feature if operators need `apt-get source` offline.

## Decision 8: The delivery snapshot is taken by `handoff`, with the moniker provided there

- **Decision**: `package_mgmt handoff --system <moniker>` (moniker required, per spec 010's "the moniker is the only handle") takes the snapshot — marking every current verified binary as delivered to that system (`sync_mask |= bit`, exactly the `snapshot --system` semantics) — before generating the handoff artifacts. Unknown/retired monikers are refused with the spec 010 error convention; nothing is generated and no snapshot is taken.
- **Rationale**: The handoff IS the delivery event; tying the snapshot to it makes the delivery record automatic and complete (the admin never runs `snapshot` separately for a handoff), and reusing the exact spec 010 marking keeps one source of truth for what was delivered. The snapshot precedes generation so the record exists even if generation later reports excluded records (a defect state reported separately).
- **Alternatives considered**:
  - Separate `snapshot --system` step before `handoff` — rejected: an extra remembered step; the delivery record would drift from the actual handoff.
  - Snapshot taken by the operator's `bootstrap.sh` — rejected: the delivery record belongs to the admin's database (the operator system is a consumer, not a record-keeper), and the script cannot write the DB with base-install tooling (FR-007).
  - Optional moniker on `handoff` — rejected: an unmonikered handoff would silently lack a delivery record; the moniker is the only handle (spec 010 FR-001).

## Decision 9: Index fetches are signature-verified against a pinned Debian archive keyring (security hardening)

- **Decision**: `fetch_index` (the single index-fetch path used by `init` and `add`/resolver) now verifies the archive's release file before trusting any index: it fetches `InRelease` (falling back to `Release` + `Release.gpg`), verifies the signature with `gpgv` against a Debian archive keyring **pinned in the repo** (`src/package_mgmt/data/debian-archive-keyring.gpg`, a snapshot of the `debian-archive-keyring` package), then only writes the index if its bytes match the SHA256 (and size) the signed `Release` lists for the index's relative path. Any mismatch raises `IndexVerificationError` — the index is refused and never loaded. The default mirror is HTTPS (T022), so this is defense-in-depth on top of TLS: authenticity of the archive *content*, matching apt's own behavior.
- **Rationale**: previously the archive indexes were fetched unauthenticated (a bare `urlretrieve` over plain HTTP) — a MITM or compromised mirror could feed a crafted index whose `Filename`/checksums then drove the download and handoff write paths. Because the indexes are the *trust input* for everything else (resolution, `Filename` → pool writes, handoff content), they are verified at fetch time. The keyring is pinned in-repo (not read from the system) so the trust anchor is deterministic across machines and CI. The `file://` operator-side handoff is *not* affected — that flow keeps its own trust model (research Decision 2; the operator's `Release.gpg` is signed by the admin's cache-local key, not Debian's).
- **Loopback exemption**: `release_base_for(mirror, release)` returns None (verification skipped) for loopback mirrors (`127.0.0.1`/`localhost`/`::1`). These are the admin's own machine or a local test archive — there is no on-path attacker, and a self-signed/local key would not be in the Debian keyring. This also keeps the integration suite hermetic (the fixture mirror is loopback). Remote mirrors are always HTTPS (T022) and always verified.
- **Alternatives considered**: (a) verify only over plain HTTP — rejected: HTTPS alone does not authenticate archive content against a compromised mirror, and apt itself verifies signatures over HTTPS; (b) a config toggle defaulting off — rejected: would silently weaken the default; (c) enforcing the Release `Suite`/`Codename` to match the configured release — deferred: the pinned keyring + checksums already prevent a mismatched release from feeding indexes, and the configured release is used in the URL path itself.

## Empirical Appendix

Experiments run on this machine (Debian Trixie, apt 3.0.3, `gpg 2.4.x`) against the generated handoff / a scratch repository under `/tmp/opencode/` (repo + key + scratch apt `Dir::State::lists`/`Dir::Cache`/`sourcelist` overrides; a real minimal `.deb` built with `dpkg-deb`):

1. Signed `InRelease` + `signed-by`, no `trusted` → `W: No Hash entry … InRelease` + `E: provides only weak security information`; index not fetched — same as `Release` + `Release.gpg` when the `Release` has a trailing blank line before the hash blocks (Debian control format terminates the section there, so apt never parses the hashes).
2. No signature files + `[trusted=yes]` → `apt update` OK (one "No Hash entry … Release" warning); `apt-get install --download-only demo-pkg` downloaded the `.deb`.
3. `[trusted=yes signed-by=<armored key>]` + valid `InRelease` → `apt update` exit 0, but the index is NOT fetched ("Unable to locate package") — the clearsigned release file cannot be hash-anchored via `file://`, and apt silently drops the index even under `trusted=yes`. Same result with `[trusted=yes]` alone + `InRelease`.
4. Release hash entries with paths relative to `dists/{release}/` are required; without them the index is silently dropped ("Unable to locate package").
5. Binary detached `Release.gpg` via `file://` → "unsupported binary format"; armored detached `Release.gpg` + `signed-by` → `apt update` OK with **zero warnings** and the index IS fetched — provided (a) the `Release` has no blank line before the hash blocks and (b) the hash blocks list both `Packages` and `Packages.gz`. Tampering with the `Release` after signing → `E: The repository ... is not signed` (signature enforced; verified via `gpgv`/tamper test). Packages resolve and the `.deb` is retrievable (verified with `apt-get download` in the integration suite).
6. `Valid-Until` present (1y) — no expiry warnings.
