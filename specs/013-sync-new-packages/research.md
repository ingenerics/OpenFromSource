# Research: Sync New Packages

**Feature**: [spec.md](spec.md) | **Phase 0** — decisions consolidated from the spec (010/012 context), the constitution, and the existing codebase (`handoff.py`, `snapshot.py`, `paths.py`, spec 012 research/contracts).

## Decision 1: The admin delta export is a new `package_mgmt sync --system <moniker>` command; roles.md's documented-but-unimplemented bulk-ingest `sync` is renamed `ingest` to free the name

- **Decision**: A new admin-only `package_mgmt sync --system <moniker>` command generates the minimal diff cache at `{binary_cache}/diff/` and takes the spec 010 delivery snapshot for exactly the binaries it ships. The spec 012 `handoff` command (full) is unchanged. The operator-side script shipped in the diff is `apply.sh`, sibling of the full handoff's `bootstrap.sh`. Because `sync` was documented in roles.md as the admin's apt-offline bundle bulk-ingest (an alternative cache-build-up path), that entry is renamed `ingest` in roles.md so the delta export owns the `sync` name.
- **Rationale**: The feature is literally "sync new packages" — a dedicated `sync` command is the most discoverable name for the incremental delivery flow, and it keeps the full handoff (`handoff`) distinct from the delta (`sync`): one command per artifact, no flag that changes the output directory or the shipped script. The `sync` command reuses the entire spec 012 generator machinery (verified-record walk, cached-index loading, `Filename`/`Size`/`SHA256` enrichment, paragraph emission, gzip, `Release` checksums, cache-local signing via the persistent `.gnupg` keyring, script emission) — no new download/parse/sign machinery, matching the feature request's and spec 012's "don't over-engineer" ethos. The bulk-ingest `sync` was documented in roles.md but never implemented (it is absent from `cli/main.py`), so renaming it to `ingest` is a documentation-only change that resolves the name collision without touching any code. The mechanism (command name and shape) is explicitly a planning decision in the spec assumptions.
- **Alternatives considered**:
  - A `--diff` flag on the existing `handoff` command (`handoff --diff --system`) — rejected: a flag that changes the output artifact (full `handoff/` vs `diff/`) and the shipped script (`bootstrap.sh` vs `apply.sh`) muddies what `handoff` means; the generator reuse is preserved regardless of the CLI surface, so a dedicated command is clearer.
  - A generic `diff` command — rejected: `sync` is the feature's name and reads as the delivery verb ("sync the new packages to a system"); a dedicated `sync` command is the most discoverable surface.
  - Keeping roles.md's bulk-ingest `sync` and naming the delta export something else — rejected: contradicts the feature name and the explicit directive to call the command `sync`; the bulk-ingest (unimplemented) is renamed to `ingest` instead.

## Decision 2: The diff carries COMPLETE per-release indexes (prior + new); minimality applies to the shipped files only

- **Decision**: The diff's `dists/{release}/.../Packages.gz` contains the paragraphs of **all** current, verified binaries (delivered + pending) whose pool files exist — the same index set a fresh full `handoff` would emit for the current state. The `pool/` inside the diff contains **only the pending binaries' files** (real copies — they must physically ship; unlike the handoff's `pool -> ../pool` symlink, there is no existing pool on the receiving side to point at). The operator-side apply replaces the handoff's `dists/` with the diff's complete ones.
- **Rationale**: FR-002 requires apt to present prior + new together after apply. Shipping complete indexes means the operator-side apply is a **wholesale replacement**, not a bash index merge (merging deb822 paragraphs in bash is exactly the kind of fragile machinery the project avoids — see spec 012 Decision 6). Indexes are a small fraction of cache size (spec 012 plan: "the handoff is a small fraction of the cache size"), so complete metadata does not violate FR-003's minimality, which is about the shipped *bytes of package content* — only new files cross the boundary (Constitution IV). A side benefit: replacing the handoff `Release`/`Release.gpg` refreshes `Valid-Until` on the operator side (spec 012 Decision 5's +1y window) at each apply.
- **Alternatives considered**:
  - Incremental index (only new paragraphs) + operator-side merge with the existing `Packages.gz` — rejected: requires bash deb822 merge/de-dup logic, error-prone and untestable with base-install tools.
  - Ship the diff pool as a symlink like the handoff — rejected: the operator's pool is on *their* media/system, not alongside the diff; the new files must physically accompany the diff.

## Decision 3: Ordering safety is a manifest "base set" — the apply checks that every previously-delivered file exists in the operator's pool before changing anything

- **Decision**: The diff carries `manifest.txt` with one line per indexed file: `new|delivered <sha256> <size> <pool-relative-path>`. `new` lines are the pending binaries (their files ship in `diff/pool/`); `delivered` lines are the current+verified binaries already marked delivered to the system (their files must already be in the operator's pool). Before any modification, `apply.sh` verifies every `delivered` path exists under the operator's pool; a missing one means an intermediate diff was missed → refuse with clear guidance (FR-011).
- **Rationale**: The spec 010 snapshot model has no snapshot table/sequence — the `sync_mask` bits ARE the record. A monotonic sequence number would add state with no schema change possible (spec 011 freeze) and would not, by itself, guarantee the operator actually has the files. The presence check is self-contained: it validates the exact failure mode ("apt would see a package whose file is missing") at the point where it can be caught cheaply (one `stat` per delivered file), and it doubles as a structural integrity check of the operator's baseline. It needs no new tables and no snapshot history.
- **Alternatives considered**:
  - A per-system snapshot sequence number carried in the diff and compared against an operator-side "applied marker" — rejected: adds state to the operator cache and the admin DB with no schema change possible; the presence check subsumes it.
  - Hash of the delivered set — rejected: heavy to compute and compare per diff; the presence check is simpler and directly tests the invariant.

## Decision 4: Integrity model — new files are SHA256-verified by the apply before entering the pool; the delivered base set is presence-checked only

- **Decision**: For each `new` line, `apply.sh` verifies the diff's file against the manifest SHA256 (and size) before copying it into the operator's pool (copy to a temp name in the pool, verify, atomic rename). For each `delivered` line it checks existence only (FR-011 base set); deep re-verification of the delivered pool is the administrator's pre-ship `verify` responsibility, consistent with spec 012's deferral (the operator cannot run `package_mgmt verify` on a bare install).
- **Rationale**: The new files are the only content crossing the boundary in this feature; verifying them is cheap (bounded by diff size) and prevents a corrupt/tampered diff from ever entering the pool. The delivered pool was verified admin-side at baseline and its integrity is re-established by the base-set presence check; re-hashing the entire delivered pool on every apply would be O(cache) and duplicate the admin's `verify` (spec 012 Decision 6's same deferral).
- **Alternatives considered**: deep re-verification of the whole pool on apply — rejected as over-engineering (duplicates admin `verify`, deferred per spec 012 precedent); structural-only preflight for new files — rejected: the new files are the payload and must be trustworthy before they are installed.

## Decision 5: The snapshot is taken by `sync`, marking exactly the binaries the diff ships — mirroring spec 012 Decision 8

- **Decision**: `package_mgmt sync --system <moniker>` computes the pending set (current + verified, `sync_mask` bit unset), generates the diff, then calls the existing `mark_delivered(conn, system, shipped_ids)` — marking exactly the pending binaries the diff actually delivered (never the delivered superset, never excluded records). A second run then sees zero pending, produces no new diff, and reports 0 (FR-006 idempotency). The snapshot IS the delivery record, so the process repeats without bound (FR-014).
- **Rationale**: Reuses the exact spec 010 marking semantics (`mark_delivered`), identical to the full handoff (spec 012 Decision 8), so the admin never runs `snapshot` separately and the delivery record never drifts from the shipped payload.
- **Alternatives considered**: separate `snapshot` step — rejected (spec 012 Decision 8's drift argument); marking the whole verified superset — rejected: would advance the snapshot past binaries that failed to ship (missing pool file / unconfirmable), losing them from every future diff.

## Decision 6: Multi-release caches are served fully — the diff mirrors the handoff's per-release suites

- **Decision**: Like the full handoff, the diff emits one complete index set per configured (release, component) whose cached archive index exists, plus one `Release` + `Release.gpg` per release, and the `apply.sh`/manifest/base-set cover every release. The operator-side apply replaces the handoff `dists/` across all releases it ships.
- **Rationale**: A cache serving trixie + trixie-backports must keep both suites consistent after apply; a diff covering only one release would silently break the other. Reusing the handoff's `_component_bases` grouping keeps behavior identical between full and diff modes.
- **Alternatives considered**: single-release diffs only — rejected: inconsistent with the handoff's multi-release support and would strand backports updates.

## Decision 7: `apply.sh` mirrors `bootstrap.sh`'s shape — optional cache-dir argument (default = the diff's parent), root requirement, testable plain-bash functions

- **Decision**: `apply.sh [<cache-dir>]` — the cache directory is an optional positional argument (used as-is when given), defaulting to the directory the script ships in (the diff's parent, i.e. the cache it was copied into). It requires root, preflights the diff structure and the release match (the same `handoff_complete`/`release_match` helpers `bootstrap.sh` uses, embedded in the script), then base-set check → copy new files → replace handoff `dists/` → `apt update`. No `--remove` (reverting an applied diff is explicitly out of scope per spec assumptions). The operator flow is implemented as plain bash functions taking explicit paths, unit-tested by sourcing the shipped script with scratch paths (same pattern as `bootstrap.sh`, contracts/cli.md — no test hooks, no root, no host modification).
- **Rationale**: FR-007 demands the apply run with only base-install tools; a bash script is the only option that satisfies it without shipping a Python toolchain (spec 012 Decision 1's argument applies unchanged). Keeping the same argument/root/preflight conventions as `bootstrap.sh` gives the operator a consistent interface between the two artifacts.
- **Alternatives considered**: a `package_mgmt apply` command on the operator system — rejected (FR-007, tool not installed on bare systems); requiring the cache-dir always — rejected: defaulting to the diff's parent matches `bootstrap.sh`'s "the cache the script ships in" convention and needs no argument for normally-placed caches.

## Empirical Notes

No new experiments were required: the apt consumption model (`file://` + `signed-by` the handoff's `offline-cache.gpg` + armored detached `Release.gpg`, `Release` hash-path rules, `Valid-Until`) is already empirically verified for the handoff (spec 012 research, Empirical Appendix). The diff reuses that exact artifact family (indexes, `Release`, `Release.gpg`, keyring), so the operator-side apt behavior is unchanged by construction. The one new mechanism — the manifest/base-set file — is plain text consumed by bash with `while read`, `cut`, `stat`, and `sha256sum`, all verified base-install tools.
